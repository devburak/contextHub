- 55 collections: 214 matching declared indexes, zero missing declared indexes, six duplicate schema declarations, zero extra actual indexes. The proposed new token/member indexes were not yet declared at audit time.
- One options mismatch: `BillingCheckoutSession.expiresAt_1` has no TTL in production although the schema declares `expireAfterSeconds: 0`. No change was made: adding TTL would automatically delete billing records and requires a separate retention decision.
- `$indexStats` is unauthorized (MongoDB code 13) for all 55 collections. No index was dropped, and no unused-index conclusion was drawn. Usage counters must be gathered with suitable privileges and an observation period covering normal traffic.

## Changes

- Add unique `{hash: 1}` for `ApiToken` and `{userId: 1, status: 1}` for `Membership`, both declared in schemas and guaranteed during API startup. Existing indexes remain in place.
- Archive statistics aggregate total and year/month counts in MongoDB, preserving tenant/status filtering, totals including undated content, month formatting and the previous server timezone. No content bodies or per-content dates are transferred to the API process.
- Tenant list owner counts use one aggregation. Roles are fetched in one batch for tenant lists and auth membership summaries; legacy role repair still uses the existing behavior when needed. Tenant plan/feature summaries remain intact.
- Admin lists already request `view=summary`. The external content API default remains `full`.
- Category/sort indexes, form uniqueness indexes, dynamic collection field indexes, regex search changes and index removals are deferred pending representative workload measurements. They were evaluated, not silently installed.

## Optional MFA behavior

All users can add an authenticator app (TOTP) and/or an email code in Profile. Enabled accounts choose either configured method or a one-time recovery code when signing in. Owner/admin accounts receive an optional reminder with a seven-day snooze. Existing accounts keep their current access until they finish setup; there is no mandatory migration deadline.

Both password and Google sign-in stop before issuing a session when a factor is enabled. A separate HttpOnly, Secure, host-only, five-minute challenge cookie cannot authenticate API requests. Origin checks protect pending-cookie POSTs; authenticated settings also require session CSRF. MongoDB enforces five attempts, expiry and atomic challenge consumption across workers. TOTP steps and recovery codes cannot be reused across challenges. Email codes are challenge-bound HMACs, expire in five minutes, have a shared 60-second resend cooldown and per-address mail quota. Only global SMTP is used.

TOTP secrets use AES-256-GCM with the user's ID as authenticated context. Eight random 128-bit recovery codes are shown once and stored as hashes. Setup requires current-password proof or a recent linked Google sign-in; changing an enabled account's settings also requires MFA within five minutes. Enabling/disabling/regenerating increments tokenVersion, signs out other devices and renews the current session. Password reset does not disable MFA. Security changes are audited without secrets/codes.

Registration now returns the same immediate `202` message for eligible/new/existing accounts. Background registration and email work do not expose account data or return an account-specific `409`. Schema validation and per-IP/per-email throttles still apply.

## Deployment and rollback constraints

1. Preserve all existing production configuration and keys. Create `AUTH_MFA_CREDENTIALS_KEY` only if absent (base64 of 32 random bytes); store a private backup. Never print it, commit it, or replace it while enrolled accounts exist.
2. Deploy the MFA-capable API with `AUTH_MFA_ENABLED=false`, build/deploy hosted Admin with `VITE_API_URL=https://api.ctxhub.net/api`, and verify health/ready, Google config, public asset bytes, auth boundaries and required indexes.
3. Enable `AUTH_MFA_ENABLED=true` and reload all workers from `.env`. This only opens enrollment; existing enrolled accounts always retain the factor requirement, even when the flag is later disabled.
4. After any account enrolls, do not roll back to an API or Admin version lacking MFA. Disable new enrollment and roll forward with MFA-capable code instead. Keep the credentials key and challenge collection. Pre-MFA rollback would bypass the factor gate (API) or break factor sign-in (Admin).
5. No root/Nginx changes are required for this release. Existing security headers and HTML no-cache rules remain active.

Configure only the selected release env file (values are never printed):

```sh
node scripts/configure-mfa.cjs --prepare --backup-dir /private/secure-backup
node scripts/configure-mfa.cjs --enable --backup-dir /private/secure-backup
node scripts/reload-api-pm2-with-env.cjs --reload
```

`--disable-enrollment` closes new setup without removing keys or bypassing enrolled accounts. Preparation preserves an existing key and an already-enabled flag.
